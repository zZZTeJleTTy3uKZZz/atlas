# Changelog

## 0.3.12 — ошибки команд стали машинно разбираемыми (#1312)

Контракт `{event, code, message}` завели в 0.3.8, но наполнили только новые
места: **201 сообщение** продолжало печататься через `console.print("[red]…")` +
`typer.Exit`, минуя обёртку. В `--json` агент получал rich-разметку — по ней
нельзя ни отличить успех от отказа, ни понять причину. Теперь таких мест **0**.

Коды взяты из единого словаря (`not_found`, `slug_taken`, `bad_priority`,
`invalid_transition`, `precondition`, `forbidden`, `conflict`, `broken_data`…),
а не выдуманы на каждое место: агент ветвится по коду, и одинаковые ситуации в
разных группах команд обязаны звучать одинаково. Тексты сообщений сохранены
дословно — снята только разметка.

Инвариант `tests/test_error_contract_coverage.py` держит три правила:
- ни одной пары «красная печать + выход из команды» (печать **без** выхода —
  это вывод результата или предупреждение, контракта ошибок не касается);
- код — snake_case-идентификатор, а не фраза для человека (нашёлся `"CONFIG"`);
- код не generic: `error`/`failed`/`unknown` не говорят агенту ничего сверх
  факта неудачи.

Проверено на реальном процессе: `project get nosuch` → `not_found`,
`type add --group bogus` → `bad_kind`, невалидный slug → `invalid_slug`.


## 0.3.11 — навык описывает флаги, которые ОТКРЫВАЮТ сценарий (#1603)

Ревизия сразу после #1602 нашла тот же разрыв на уровне флагов:

- **`--modules` / `--all` у `project list`.** В 0.3.7 модули скрыли из вывода по
  умолчанию — и не написали, чем их показать. Агент видит список без модулей и
  делает вывод, что их нет. Изменение поведения без обновления карты — ровно то,
  с чего начался #1602.
- **`--entity-kind` у `project update`.** Штатный способ выбраться из отказа
  «— idea-запись, а не проект портфеля» (0.3.2), в навыке не упоминался: агент
  упирался в ошибку без пути наружу.

Инвариант расширен: проверяются не только команды, но и флаги-сценарии
(`--to-project`, `--as epic`, `--reviewer`, `--modules`, `--all`,
`--entity-kind`). Обычные флаги-поля (`--email`, `--ends-at`) перечислять не
нужно — навык ссылается на `atlas <group> --help` как на источник правды, и
раздувать список означало бы дублировать справку.


## 0.3.10 — навык знает про перенос задач; тупик «review без приёмщика» закрыт

**Навык не описывал `task move` / `epic move` / `unconvert` (#1602)** — команды
работают с 0.3.8, но в `SKILL.md` и `references/commands.md` о них не было ни
слова. Агент читает навык, а не `--help` каждой из 135 команд, поэтому на вопрос
«перенеси задачу в другой проект» честно отвечал, что Atlas так не умеет.
Функциональность была, до потребителя не доехала.

Починено не текстом, а инвариантом: `tests/test_skill_covers_cli.py` сверяет
список команд CLI с текстами навыка и падает, если команда есть в коде, но не
описана. Отдельно проверяются ключевые связки ровно теми словами, которыми их
спрашивают (`task move`, `--to-project`, `--as epic`) — иначе `move` от
`project git move` создавал бы ложное ощущение покрытия.

**`task submit` без приёмщика больше не создаёт тупик (#1316)** — в `done`
переводит только назначенный reviewer, поэтому `review` с `reviewer=None` не
закрывался никогда. На портфеле так висели три задачи: 2, 22 и 23 дня.
- `submit` без reviewer отвергается и называет три выхода: назначить приёмщика,
  закрыть соло через `task done`, включить приёмку глобально;
- **`task update --reviewer <slug>`** — флага не существовало вовсе: приёмщика
  можно было задать только при создании, то есть выбраться из тупика было нечем
  (моя же подсказка советовала несуществующий флаг — поймал тест);
- `task triage` отдаёт `review_without_reviewer` отдельным списком: гейт на
  `submit` не лечит записи, которые уже в базе.


## 0.3.9 — `git move` не бросает БД в рассинхроне (#1124)

`glab repo transfer` может вернуть ненулевой код (таймаут, неожиданный формат
вывода, повтор уже выполненной операции) тогда, когда GitLab репозиторий **уже
перенёс**. Команда выходила по этой ошибке ДО обновления БД и локального
`origin`, оставляя ровно тот симптом, с которого началась задача: «в GitLab
перенесено, а Atlas показывает старый URL».

Теперь коду возврата не доверяем — проверяем факт: лежит ли репозиторий по
ожидаемому новому пути.

- лежит → доводим локальный `origin` и БД, **предупреждая** пользователя, что
  `transfer` вернул ошибку (в выводе появляется `recovered: true` — молчать об
  этом нельзя);
- не лежит → честный отказ, БД не тронута, в сообщении — чем сверить состояние
  (`atlas project git sync-from-remote <ref>`).


## 0.3.8 — двусторонний backlog, перенос между проектами, контракт ошибок

**Обратный путь task/epic → пул `backlog` (#1301)** — дорога была
односторонней: обратно только `task cancel` + ручной `backlog add` с копипастом.
Теперь `task unconvert` / `epic unconvert`, возврат — привычным `backlog convert`
(`--as task` или новый `--as epic`). Эпик уходит и возвращается КАСКАДОМ: его
задачи становятся записями пула со ссылкой на запись эпика и поднимаются вместе
с ним.

Что решено по ходу и почему:
- **статус задачи не меняется** — `cancelled` соврал бы (задача не провалилась,
  а вернулась в раздумья), а свой `converted` потребовал бы правки CHECK;
  запись просто архивируется, а чем стала — видно по записи пула;
- **slug освобождается** (архивная получает суффикс `~<id>`), иначе возврат не
  вернул бы прежнее имя: оно глобально уникально;
- **номер не восстанавливается** — он тоже уникален и остаётся за архивной
  записью; прежний лежит в payload как след, для ссылок хватает slug;
- **ЦКП, описание и связи едут в `origin_payload`** — без этого возврат был бы
  тем же копипастом, только через БД.

**Перенос между проектами (#1126)** — `task move --to-project` и
`epic move --to-project`. Раньше пути не было вообще: оставалось пересоздать
задачу вручную, потеряв историю и номер. Запись сохраняется целиком, slug
пересобирается под prefix нового проекта (иначе он врал бы о принадлежности).
Эпик переносится ВМЕСТЕ с задачами — связь эпик↔задача внутрипроектная (#1125),
и оставить задачи значило бы её разорвать; при переносе одной задачи связь с
эпиком прежнего проекта снимается по тому же правилу.

Миграция `b1c4e7f20a91`: `backlog_items` получает `parent_id` (каскад эпика) и
`origin_kind/origin_ref/origin_payload` (возврат). Все колонки nullable —
существующие записи валидны без правки данных.

**Контракт ошибок у всех команд (#1306)** — `@command` (clikit) ловит `CliError`
и печатает его через `emit_error`: в `--json` режиме ошибка приходит объектом
`{event, code, message}`, а не rich-разметкой, ломающей машинный разбор.

Заявка была про `task add`/`update`, но аудит показал **19 команд из 131** без
обёртки — почти весь `projects.py` (`add`, `update`, `delete`, `archive`,
`move`, `reorganize`, работа с тегами и участниками). Обёрнуты все; новая
команда без `@command` теперь роняет сьют (`tests/test_command_contract.py`).

Гейт «эпик чужого проекта» (#1125) переведён на `CliError` — в 0.3.7 он был
вынужден печатать текстом, потому что `task add` контракта не имел.

⚠️ Механизм наполнен частично: **202 ошибки** в командах всё ещё печатаются
через `console.print("[red]…")` и в `--json` выводе остаются текстом. Перевод —
задача #1312 (правка механическая, но каждой ошибке нужен осмысленный `code`).

**Удалён мёртвый код idea/inbox (#1305)** — 1533 строки исходников
(`ideas.py`, `commands/ideas.py`, `commands/inbox.py`) и 501 строка их тестов.
Модули не были зарегистрированы в `cli.py` — вызвать их было нельзя; их роль
занял пул `atlas backlog` (активных `idea`/`inbox` в базе — 0). Инвариант
подсказок больше не нуждается в исключениях и проверяет весь `src/`.

**Фикс регрессии 0.3.7** — в `project git sync-from-remote` использовался
`CliError` без импорта: проект без remote давал бы `NameError` вместо
сообщения. Путь редкий, тесты его не покрывали — поймал `ruff` (тот самый
линтер, возвращённый в CI в 0.3.6).

## 0.3.7 — портфель без внутренностей, честный git-diff, зарезервированный `modules/`

**`project list` показывает портфель, а не всё подряд (#917)** — модули (проекты
с родителем) по умолчанию скрыты: это части контейнера, а не отдельные единицы.
На реальном портфеле список 85 → 75 строк. Скрытие не бесследное: у контейнера
появилась колонка `modules` с числом (`peretyazhka 4`, `vpn-checker 2`).
Показать модули: `--parent <ref>`, `--modules`, `--all`; `--standalone` совпадает
с умолчанием. Взаимоисключающие флаги области падают, а не выигрывают молча.

**`project git sync-from-remote` перестал врать (#925)** — URL сравниваются после
нормализации (`.git`-суффикс, регистр хоста и namespace, `ssh`/`https`, слэш на
конце). Было: сырое сравнение строк показывало «расхождение» у **32 проектов из
32** и предлагало переписать URL на эквивалентный. Стало: 0 — команда снова
сигнал, а не шум. Пустой URL не совпадает ни с чем, включая другой пустой.

**Задача не попадёт в эпик чужого проекта (#1125)** — `Epic.slug` уникален
глобально, а резолв искал эпик по всей базе без сверки с проектом задачи.
`task add --project a --epic <эпик-проекта-b>` молча привязывал задачу к чужому
эпику — связь уводила её в другой проект. Проверка оказалась нужна не только в
`batch` (как в заявке), но во всех входах: `task add`, `task update`, `batch`.
Сообщение называет проект-владелец и путь к исправлению.

**`epic add` на занятый slug (#1127)** — вместо сырого `IntegrityError` со
стектрейсом и путём в site-packages: понятный отказ с указанием эпика-владельца
и его проекта. Автоматический slug из заголовка теперь берёт следующий свободный
(`-2`, `-3`, …) — как в `task add`, где это работало с самого начала.

**`task checklist add --text` заработала (#1131)** — глобальные флаги вывода
поднимаются из argv до Typer, и `--text` съедался как флаг, а не как содержимое
пункта: команда падала с «Missing option --text» в любой оболочке, то есть была
неработоспособна полностью. Теперь для команд с собственной `--text` хойст
отключается; реестр таких команд стережёт тест — вторая появится, тест упадёт
раньше пользователя.

**Подсказки CLI зовут существующие команды (#1128)** — после перехода на канон
в единственном числе в сообщениях остались `atlas tags add`, `atlas logs`,
`atlas statuses list`, `atlas types list`. Хуже: устаревшие команды сидели в
**шаблонах `README.md`/`AGENTS.md`, которые Atlas пишет в каждый новый проект** —
и закреплялись там навсегда. Исправлено 25 мест; инвариант проверяет все
сообщения (AST, без докстрок) против списка живых групп.

**`project git sync-from-remote <ref>` (#1129)** — можно сверить один проект;
раньше принимался только весь портфель, то есть десятки сетевых запросов ради
одной записи.

**`modules/` зарезервирована раскладкой (#938)** — `project layout verify` теперь
репортит `modules_not_reserved`, если в `modules/` лежит не-junction. Папка
предназначена для ссылок на `_storage/<slug>` проектов-модулей; обычный пакет с
тем же именем схлопывается с раскладкой — junction модуля попадает внутрь пакета
и ломает импорты, а `layout sync` рискует снести код. Внутренние части проекта →
`components/`. Правило записано в `SKILL.md` и `references/projects-and-layout.md`.
Проверка на портфеле: 8 проектов с настоящими junction — чисто, 5 нарушителей
найдены.

## 0.3.5 — чистая установка навыка: allowlist вместо .skillignore (#936)

Механизм из 0.3.4 **не сработал**: `skills/atlas/.skillignore` попадает в опись
файлов хаба, но до папки навыка не доезжает вообще, а без файла skillkit
фильтрацию не включает («иначе ничего не делаем»). После обновления на 0.3.4 в
навыке по-прежнему лежали `src/`, `pyproject.toml`, `install/`, `CHANGELOG.md`
и копия `skills/atlas/`.

Состав установки теперь задаёт **allowlist `files:` во frontmatter `SKILL.md`** —
он читается из самого `SKILL.md`, который доезжает всегда. Решение проверено
прогоном настоящего `skillkit.filter` на копии структуры стора:

```yaml
files:
  - /SKILL.md
  - /_skill_meta.toml
  - /agents/**
  - /references/**
  - /.venv/**
```

Две детали, без которых оно ломается (обе поймались на прогоне, не в теории):
- **якоря `/`** — без них `SKILL.md` матчится на любом уровне (gitignore-
  семантика), и вложенная копия `skills/atlas/SKILL.md` переживает фильтр;
- **`/.venv/**`** — allowlist удаляет всё неперечисленное, а per-skill venv
  (65 МБ, из него работает CLI-шим `atlas`) не защищён ни
  `_PRESERVED_ROOT_NAMES`, ни `preserved_paths`: последний skillkit хардкодит и
  из манифеста не читает. Без этой строки первый же update снёс бы venv вместе
  с рабочей командой `atlas`.

Тесты `tests/test_skill_payload.py` переписаны под allowlist и стерегут оба
требования плюс покрытие всех файлов тела навыка.

## 0.3.4 — changelog в релизах, чистая установка навыка, онбординг с проверкой CLI

**Доставка changelog (#926)** — способ ведения `CHANGELOG.md` не меняется,
механизируется только доставка. Раньше описание релиза не доходило никуда:
теги на github были lightweight, GitHub Releases не создавались (0 на 12 тегов),
на PyPI не было даже ссылки.
- `scripts/release_notes.py` — извлекает секцию версии; один и тот же текст идёт
  в аннотацию тега, в GitHub Release и в проверку CI.
- Тег на github теперь **аннотированный**, с телом секции (`publish_public_github.sh`),
  причём с `--cleanup=verbatim`: по умолчанию `git -F` вырезает строки на `#`,
  то есть заголовок версии молча пропадал бы из каждого тега.
- **GitHub Release** создаётся тем же скриптом через Releases API (первый релиз
  на 13 тегов). Шагом в `.github/workflows/publish.yml` это сделать нельзя:
  публикация в github идёт PAT-ом без scope `workflow`, и GitHub отвергает пуш
  целиком, если в нём меняется хоть что-то в `.github/workflows/`. Повторный
  прогон тега обновляет существующий релиз, а не плодит второй.
- `[project.urls]`: `Changelog`, `Release Notes`, `Issues` — PyPI показывает их
  отдельными ссылками с иконками (PEP 753).
- Джоба **`release-guard`** в GitLab CI падает ДО публикации, если версия
  разъехалась (`pyproject` / `__init__` / манифест навыка / pin `atlas-pm` / тег)
  или в `CHANGELOG.md` нет секции для тега. Версии на PyPI неизменяемы —
  ловить рассинхрон нужно до, а не после.
- `atlas update --check` отдаёт `release_notes_url` и печатает «что нового»:
  `CHANGELOG.md` в wheel не попадает, а страница PyPI показывает README.

**Установка навыка ставит только навык (#936)** — `skills/atlas/.skillignore`.
Репозиторий монорепный (CLI в `src/`, навык в `skills/atlas/`), хаб знает про
подпапку, но его опись файлов перечисляет пути от корня — поэтому на update в
папку навыка налипали `src/`, `pyproject.toml`, `install/` и даже копия
`skills/atlas/` внутри самого навыка.
- Выбран IGNORE-режим, а не allowlist `files:` во frontmatter: allowlist удаляет
  всё неперечисленное, а per-skill `.venv/` (65 МБ, из него работает CLI-шим
  `atlas`) не защищён — `preserved_paths` skillkit хардкодит и из манифеста не
  читает. Первый же update снёс бы venv вместе с рабочей командой.

## 0.3.1 — закрытие тех-долга аудита 2026-06-30 (#894)

Починены все 16 оставшихся дефектов аудита (`docs/design/2026-06-30-atlas-audit-findings.md`).

**Исправления с влиянием на данные/надёжность**
- **backup больше не пропускает проекты** [5]: гейт смотрел на legacy `git_repo_url`,
  который `git link`/`move`/`sync-from-remote` не заполняли — привязанные проекты
  молча не бэкапились. Источник правды теперь `git_remote_url` (+ зеркалирование legacy).
- **sync-демон стартовал из чужой папки** [6]: `parents[4]` (артефакт rename pm→sync)
  → поиск `pyproject.toml` вверх по дереву.
- **push учитывает неудачные попытки** [13]: `mark_failed` был мёртвым кодом; теперь
  attempts/last_error пишутся, а в `failed` запись уходит только по порогу (5) —
  одиночная сетевая ошибка не выбрасывает событие из очереди.
- **pull различает applied/skipped** [12]: пропущенные события (гонка порядка доставки)
  больше не считаются применёнными и видны в логе `watch`.
- **archive атомарнее** [17]: новый junction создаётся ДО снятия старого.

**Поведенческие изменения**
- `task reject` возвращает задачу в **todo** (было `in_progress`) [10] — `submit` снимает
  lease, а `in_progress` без lease нарушал инвариант. Брать заново — `task start`.
- `task reject` **только из `review`** [4] (принимал `blocked` в обход lease-гейта `unblock`).
- `task approve` проверяет reviewer-гейт ДО идемпотентного закрытия и не пишет
  approve-комментарий, если перехода не было [9].
- `task reopen` сбрасывает `started_at` [16] (иначе lead-time считался от первого старта).
- `project git init` **не падает на кастомном типе** [11] — fallback `products`, как в layout.
- `backlog archive` запрещён для уже `converted` идеи [19] (`--hard` по-прежнему удаляет).
- `backlog`-команды по legacy idea/inbox дают предметный маршрут в `atlas project` [8];
  `backlog add` не занимает slug legacy-записи [14]; `--project` не принимает idea/inbox [15].
- Глобальные `--json/--text` уважают POSIX-сентинел `--` [20].

## 0.3.0 — RESTful-канон срезов CLI (BREAKING)

Приведение поверхности CLI к канону `<ресурс> <глагол>` (методология kit-integration):
подчинённые ресурсы вложены в родителя (как `epic worktree` / `project git`),
плоские дефисы и дубли убраны. **Чистый разрыв — старых имён больше нет.**

### Migration (старое → новое)

| Было | Стало |
|---|---|
| `atlas member add --task <t> …` | `atlas task member add <t> …` |
| `atlas checklist add --task <t> …` | `atlas task checklist add <t> …` |
| `atlas project member-add <p> …` | `atlas project member add <p> …` |
| `atlas project member-list/-remove` | `atlas project member list / rm` |
| `atlas project add-tags / remove-tags` | `atlas project tag add / rm` |
| `atlas participant …` | `atlas person …` (домен `Participant` не меняется) |
| `atlas type edit <t> …` | `atlas type update <t> …` |
| `atlas logs …` | `atlas log list …` |
| `atlas action-log list …` | `atlas log raw …` |
| `atlas connect <url>` / `disconnect` | `atlas backend connect <url>` / `disconnect` / `status` |
| `atlas backup install / uninstall / list-tasks` | `atlas backup schedule install / uninstall / list` |
| `atlas config init` | `atlas config setup` |
| `atlas upgrade [--reinstall]` | `atlas update --from-git` |

### Не тронуто

- `idea` / `inbox` — остаются top-level: это НЕ дубли `backlog`, а отдельные
  сущности со своей материализацией (`idea promote` → layout/junction/IDEA.md/
  extract-backlog; `inbox` → физическая свалка `_Inbox/<slug>/`). Сведение в
  `backlog` = либо потеря функциональности, либо отдельная миграция — вынесено
  из этого релиза.
- `dash` — короткий алиас `dashboard` (осознанный UX).
- `sync up` — оставлен как есть (обёртка над `sync daemon install`).

### Notes

- Реестр людей переименован только на уровне CLI-фасада (`person`); доменная
  модель `Participant`/`ProjectParticipant` и `action_log entity_type="participant"`
  сохранены — рассинхрон CLI↔домен намеренный.
